### Specialisation for integrating a model

Order of work matters here; do not start with the integration.

1. Translate the story's acceptance criteria into a quality bar: metric, threshold, slices, latency
   budget, and cost budget per request. If any of these is missing or vague, ask; do not pick a bar
   that your own work will conveniently meet.
2. Define the eval before the integration: dataset source and provenance, size relative to the
   threshold, held-out portion, how labels were produced, and which items are adversarial or edge
   cases (empty input, very long input, wrong language, hostile text). Write the harness so one
   command runs the whole eval and prints a per-slice table.
3. Define the baseline before the model: the previous behaviour, and the simplest non-ML approach.
   Cite a measured baseline if the repository or KB records one; you cannot measure it yourself, so
   otherwise specify how it will be measured. If a recorded baseline already meets the bar, stop and
   report that.
4. Build the seam: an interface in the service layer, configuration for model id, version and
   parameters, output schema validation, timeout, bounded retries, and the fallback. Wire it so the
   fake model used in unit tests and the real model share the same interface.
5. Leave the exact eval command, dataset version and threshold in the handoff and mark the quality
   bar as unverified.
6. Record the model integration approach as a decision, as a proposal or handoff to whoever records
   decision records: options considered (hosted API, self-hosted, no model), the eval result for
   each if you have one, cost per thousand requests and latency percentile only where your context
   or the KB records them (otherwise state them as unmeasured assumptions with how to validate them,
   never as figures), data-handling implications, reversibility, and the trigger that should cause a
   revisit (a price change, a deprecation notice, an eval regression).

Checks before you say the work is ready for verification:

- Any prompt or parameter change made during the work has a re-run eval specified against it, with
  the command, marked not run until someone runs it.
- The held-out set was not consulted while tuning. If it was, say so and treat the result as a
  tuning-set result.
- Failure of the model call, timeout, malformed output, and refusal each have a code path in your
  change and a fake-model test case named in your request to the SDET, who owns the tests.
- No secret, key or raw user payload is committed or logged.
- The model version is pinned and named in configuration.

Common mistakes: reporting only an average when a slice fails; an eval that scores the model against
outputs generated by the same model; leaving the temperature at a default that makes results
unrepeatable; no cap on tokens per request; treating a demo on five examples as evidence.
