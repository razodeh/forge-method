## 1. How the 37 pinned steps were derived (so the numbers can be re-checked)

`test/output-contract-known-gaps.test.ts` pins 37 = 28 `no-write-grant` + 9 `no-write-scope`. I
re-derived it from `WORKFLOW_INDEX`, `modules/*/workflows`, `loadAgentRegistry`, `outputGlob` and
`outputPathCoveredBy`: 57 agent steps in the `steps:` of all shipped workflows (a 58th,
`build-stage`'s `onComplete` `em` step, is never compiled: D11); 38 declare `outputs`; 8 declare
`produces`; none declares both; 30 are assigned to a `write: false` agent (28 with outputs, plus 2
without: A6). The inventory's second class, `no-write-scope`, is a **definition heuristic, not a
runtime check**: `file_ownership` is not enforced at run time and is not rendered into any prompt
block (it appears in neither `compile-prompt.ts` nor `assemble.ts`). It matters only through
`forge agent validate`'s overlap check (`packages/cli/src/commands/agent.ts:140`) and, under
`strict`, through the claim (A3). That is why the 9 rows are best fixed in the engine, not by
editing agent ownership (edit set C, section 3).

**Separation of duties.** Safe by construction: R, because the engine, not the reviewer, writes the
report, and the reviewer and critic never gain `write`. Safe with a stated residual: set A for the
ten authoring roles, because sets C and P confine each such step to its declared outputs and the
documents its brief names, and revert the rest at every autonomy level. The residual, which the
owner should read: the claim is a **type glob, not an artifact id**. `security`
(harden:security-pass) can rewrite any `DEF-*.md`, and `validate-rules.ts` treats any status other
than the literal `open` as closed, so it could close a Sev1; `po` holds every `STORY-*.md`; `em`
every `SESSION-*.md`; every HandoffRecord step can edit earlier entries in the shared `handoffs.md`;
`integration-architect` holds every `specs/interfaces/*.yaml` while `spec interfaces --check-frozen`
is unimplemented (E1). Also `enforceClaim` runs only when the session changed files (`steps.ts:212`;
Q209 records the reroll case). Mitigations that exist: G-Stable and every phase gate require a human
approval; the hard fix is a path-scoped platform grant (`Edit(<glob>)`, `07` §7.2 `extra`) or
per-artifact-id enforcement, deferred to M14. **Test-architect is one of the four protected roles**
(`05` §5.2; `REVIEW_OR_CRITIC_ROLES` at `packages/agents/src/resolve/tool-grant.ts:76` makes `15`
§15.3.2 refuse an overlay `write: true` for it). `diagnostician`, another of the four, already ships
`write: true`, so the precedent exists; the two test-architect steps author a plan and a
verification record, not the work under review. Set A includes it, but only together with P (its
plan document, `docs/forge/specs/test-plan.md`, must be inside the claim, row 16). The stricter
alternative (it stays `write: false`) leaves rows 16 and 20 failing until the engine can author
`HandoffRecord` entries; not recommended.

**The design reading.** `05` §5.3 pairs `write: false` with `git_commit: docs-only` and file
ownership over `docs/`, and `20` §20.1 defines `write` as "file creation/modification within the
step's claim". The spec intends these roles to write documents inside a claim; the shipped boolean
grant cannot say so, and `06` §6.7's own default table (`warn` at `guided`) contradicts "inside a
claim" for them. Sets C and P are what make the claim real.

## 4. Genuine product decisions, with options

**Question 1 — how do document-authoring roles deliver files?** (A1, A3)

1. _Grant write, confine by claim (recommended)._ Sets A + C + P. Cost: one engine rule, ten grant
   edits and `produces` on the affected steps; enforcement is after the fact (revert), not a tool
   boundary, with the residual in section 3.
2. _Engine materialises artifacts from the agent's answer_ (`result.md` now exists, Q210). Strongest
   SoD, no grant change. Cost: a new output protocol; every planning brief tells the agent to write
   files, multi-document outputs (Stories, NFRs) are awkward as text, and every planning brief
   changes.
3. _Path-scoped platform grant._ Hard boundary. Cost: `ToolGrant.write` becomes a path list (`07`
   §7.2, `05` §5.3, `20` §20.1 all change) and the adapter maps it; do it after 1 as hardening.

Recommendation: 1 now, 3 in M14. Option 2 is rejected because it rewrites every planning brief to
avoid a boundary that option 1 enforces anyway.

**Question 2 — who writes the swarm-review `ReviewReport`?** (A4). (a) _The engine writes and
validates it_ (recommended; edit set R): the reviewer perspectives stay read-only, the report is a
deterministic merge the engine already computes, and P7 still runs. (b) Give `reviewer` a scoped
write: refused, it is the role the separation rules protect. (c) Drop `outputs` from the two review
steps: refused, it restores the Q208-f4 "success with no file" behaviour.

**Question 3 — lane visibility** (D2). (a) _Enqueue every lane that no `merge` step consumes and
branch new lanes from the integration tip_ (`06` §6.4 point 4 as written), leaving explicit `merge`
steps (with their review-before-merge order and pre/post checks) untouched, and running read-only
inline steps at the integration worktree; (b) add `merge` steps to the 16 multi-step workflows; (c)
run planning agent steps inline in the supervisor (P7's check reads the lane diff, so this needs a
second code path). Recommendation (a): it is what the spec says, it is one place in the engine
instead of 16 workflows, and it does not remove the review gate that `build-stage` and
`implement-story` put in front of their merges. (Applying auto-enqueue to every lane, including
`implement`, is what to avoid: it would land code before `review`.)

**Question 4 — `elicit`** (D1). (a) _TTY prompt when interactive, `--answers <json>` otherwise_
(recommended); (b) TTY only (CI and tests cannot run `intake`); (c) answers only from a file (no
interactive path, `03` shows none). Recommendation (a). `subworkflow` stays deferred: only
`build-stage:deliver` uses it.

**Question 5 — test paths** (C4). (a) _Optional `Story.test_paths`_ (`09` §9.3 gains the field; DoR
rule 4 requires `files_expected` and `test_paths` disjoint; `run-plan` uses it, keeping the
heuristic as fallback); (b) keep one list plus the heuristic; (c) let `files_expected` carry tests
and drop `10` §10.6's separation. Recommendation (a): (b) leaves co-located tests unclaimed, (c)
deletes the guard `10` §10.6 calls the fix for "the single most common failure mode".

**Question 6 — running tests** (A5). (a) _Derive the exec grant from `execution.testCommands`_
(exact strings, only for roles that run tests); (b) hard-code `pnpm test*`/`pytest*` in agent YAML
(stack-specific, wrong for most projects, exceeds `frontend`'s ceiling); (c) command steps only.
Recommendation (a): one source of truth, never wider than a command the user configured.

**Question 7 — gates whose commands do not exist** (E1). (a) _Implement the 27 missing checks
(recommended)_; (b) delete or downgrade the unimplemented checks. (b) removes rigour to make a run
green and is refused. The work is three pieces because the checks are heterogeneous.

**Question 8 — G-Foundation and the deployed skeleton** (E4). (a) _Keep the spec, add a
`skeleton-deployed` check_ (a recorded dev environment, else a Waiver); (b) amend `11` F-INIT-7/`14`
§14.9 so G-Foundation needs only a pipeline plus a local smoke path. Recommendation (a): (b) weakens
a gate, and `method-guide.md` makes gate rigour fixed unless waived. The cost of (a) is one recorded
Waiver on projects with no environment yet.
