## Load-sensitive tests: measured, explicit per-file timeouts (M14 P45)

The old rule tolerated these files flaking under CI load rather than fixing it — a defensible
allowlist, but one that quietly normalised not knowing how much headroom each file actually had.
This piece measured each file's isolated run (`node scripts/run-tests.mjs run <path>`, this sandbox,
no deliberate extra load — see the methodology note below), and where a file's own slowest test or
hook came anywhere close to the global `vitest.config.ts` 60 000 ms default, gave it an explicit
timeout sized at 3× the highest measured sample, rounded up WITH real margin (not the bare next
multiple of 10 000 — a round-2 critic caught that the first version of
`test/workspace-floor.test.ts`'s `90_000` cleared its own 3× figure by only 84 ms), capped at 600
000 ms (`21` §21.1's e2e ceiling; precedent `test/agent-prompts-all-workflows.test.ts:288,856`,
`test/authoring-roles-run.test.ts:417, 425`). Where 3× measured stayed comfortably under the
existing budget (the global default, or an already-generous prior override), nothing in source
changed — adding a smaller explicit timeout than the safe default would tighten the test, not
protect it, which is the opposite of this rule's purpose. The table below is the record either way,
so "no override" reads as a measured, deliberate decision rather than an unmeasured gap.

### Methodology, honestly

This machine is not exclusively this piece's: it is the shared working tree other M14 pieces run
their own tests and typechecks on concurrently, so even an "isolated" (single-file) run carries some
ambient load, and repeated samples of the same file varied by 30-45% run to run
(`crash-resume.test.ts`: 49 864 ms then 65 709 ms, then 68 056 ms on a third sample taken later,
during Rule 14/15's clean-worktree verification, where it ran alongside 2 other files rather than
fully isolated; `verify-success-criteria.test.ts`'s SC3 test: 50 817 ms then 74 576 ms). Where a
file was sampled more than once, the table records the highest sample and sizes the 3× multiplier
from that, not a lower one — including a later, less-isolated sample if it turned out to be the
highest, which is what happened for `crash-resume.test.ts` above (a round-2 critic caught that the
first version of this file cited only the first two samples and rounded to a number, `200_000`, that
gave under 3× margin over the third). Running `run-upgrade.test.ts` and `backup.test.ts` in the same
`vitest` invocation (two file-level worker processes contending for the same CPUs) measurably slowed
both relative to running each alone — real evidence that inter-file contention is a bigger effect
here than any one file's own cost, and part of why this list stays a list of _measured_ budgets
rather than a claim that any number here holds under arbitrary load. See `M14 P45`'s own
gauntlet-log entry for the red/green, under-load demonstration on `test/intake-workflow.test.ts`
(the one file in this milestone piece that got a structural fix — one `runInit` per file instead of
nine — rather than just a timeout).
