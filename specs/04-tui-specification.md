# 04 — TUI Specification

Built with Ink 5. The TUI is a **view + command emitter** over `@forge/engine`. It holds no domain
state of its own beyond UI state (focus, scroll, filters, modal stack).

## 4.1 Design constraints

- **Minimum viable terminal:** 80×24. Degrade gracefully: below 100 cols, collapse to single-pane
  with a tab bar; below 24 rows, drop the footer help line to a single key hint.
- **Target terminal:** 120×40+.
- Unicode box-drawing by default; `--ascii` / `FORGE_ASCII=1` fallback for dumb terminals.
- Colour is meaning-bearing but never *only* meaning-bearing: every state has a glyph + label.
  (`✓ pass`, `✗ fail`, `● running`, `◐ waiting`, `⏸ paused`, `⚠ warn`, `⊘ blocked`, `↷ skipped`).
- Redraw budget: ≤ 10 fps; coalesce engine events in a 100 ms window. Long streams render into a
  bounded ring buffer (default 2000 lines/lane, configurable).
- No mouse dependency. Mouse support MAY be added for scroll only.
- All destructive actions require typed confirmation (`type "abort" to confirm`), not a keypress.

```

│                                                                                                 │
│   <active screen body>                                                                          │
│                                                                                                 │
├─────────────────────────────────────────────────────────────────────────────────────────────────┤
│ [1]Home [2]Run [3]Specs [4]KB [5]Gates [6]Sessions [7]Cost [8]Customize  ?help :cmd  q quit     │

```

Header shows: product name · current stage + progress · active lanes · spend/budget · elapsed.
When paused/blocked, the header turns to the blocked reason and the glyph changes.
It also shows `⚙ N` when N customization overlays are active, and `⚠ escalations: N` while any tool
ceiling escalation is in force — customization must never be invisible during a run.

## 4.3 Screens

Purpose: "what is the state of this product, and what should I do next?"

The **Next actions** pane is generated by the same engine logic that powers `forge help`, ranked by:
blocking-ness → gate readiness → cheapest-unblock → user's declared goal.

### S2 — Run board (the core screen)

Two-pane: lane list (left, 30%) + lane detail (right, 70%). Toggle `Tab`.
`v` cycles the right pane between **Transcript**, **Diff**, **Files**, **Checks**, **Prompt**.

```
┌ Lanes ─────────────────┐┌ Lane: story-014 · backend-engineer · ● running 4m12s ───────────┐
│ ● story-014 backend    ││ Step 3/6  implement · model sonnet · $1.14 · 22 tool calls      │
│ ● story-016 frontend   ││ ─ Transcript ──────────────────────────────────────────────────│
│ ◐ story-018 waiting    ││ 12:40:02 Read  src/billing/invoice.ts                           │
│ ✓ story-011 merged     ││ 12:40:09 Edit  src/billing/invoice.ts (+41 −6)                  │
│ ✗ story-013 failed     ││ 12:40:31 Bash  pnpm vitest run src/billing                      │
│ ⊘ story-021 blocked    ││          ✗ 2 failing — retrying with failure context            │
└────────────────────────┘└────────────────────────────────────────────────────────────────┘
┌ Scheduler ──────────────────────────────────────────────────────────────────────────────┐
│ ready 4 · running 3/4 · blocked 2 (ADR-014) · merge queue 1 · budget $4.21/$25           │
└──────────────────────────────────────────────────────────────────────────────────────────┘
```

Lane keys: `Enter` inspect · `f` follow output · `i` interject (send a message into the lane's
session) · `s` stop lane · `R` retry step · `m` request merge · `d` show diff · `o` open worktree
path in `$EDITOR`.

**Interject** is important: it lets the human steer a running agent without killing the lane. It is
delivered via the adapter's streaming-input capability; if unsupported, it is queued as an addendum
for the next step and the TUI says so explicitly.

### S3 — Specs / Spec graph

Tree: `Vision → Capabilities → Epics → Stories → Tasks`, with `Tests` and `ADRs` as cross-links.
Right pane shows the artifact rendered, its front matter, its trace edges up and down, and its
validation status.

Keys: `t` show traceability path to root · `n` new artifact from template · `e` edit in `$EDITOR`
(then auto-`forge spec validate`) · `x` show orphans only · `m` open the traceability matrix.

Traceability matrix view: capabilities × stories × tests grid with coverage marks; cells that are
empty where the schema requires an edge are rendered `✗` and are actionable.

### S4 — Knowledge Body browser

Left: KB section tree (`product/`, `architecture/`, `data/`, `delivery/`, `ops/`, `domain/`,
`decisions/`, `constraints/`, `glossary`). Right: entry with front matter, confidence, last-verified
date, sources, and "used by" back-references.

Keys: `/` full-text search · `c` show contradictions · `s` show stale entries · `v` mark verified ·
`a` new ADR from this entry · `w` show write history (which agent/run wrote it) · `o` open the
entry's rendered diagrams in the browser.

Diagrams attached to an entry render as **source + caption + alt text** in the right pane, since
inline images are not portable across terminals. Where the terminal advertises an inline-graphics
protocol the TUI MAY render the SVG inline as a progressive enhancement — never as a requirement, and
never as the only way to read the diagram. A `⬚ 2 diagrams` affordance shows the count; `o` opens
them; `D` shows a before/after diagram diff when the entry changed in the current run.

### S5 — Gates

List of gates for the current stage with status, checks, and evidence.

```
┌ G-Design · ◐ waiting on human ────────────────────────────────────────────┐
│ Deterministic checks                                                      │
│  ✓ spec:validate            0 errors                                      │
│  ✓ kb:lint                  0 contradictions                              │
│  ✓ adr:coverage             every component has an owning ADR             │
│  ✗ interfaces:frozen        3 interfaces referenced but not defined       │
│ Advisory (LLM)                                                            │
│  ⚠ architect-review         "queueing strategy under-specified for retry" │
│ Open questions (2)                                                        │
│  Q1 Multi-tenant isolation: schema-per-tenant vs row-level?               │
│  Q2 Are invoice PDFs generated sync or async?                             │
└───────────────────────────────────────────────────────────────────────────┘
[a] approve  [x] reject  [w] waive  [c] re-run checks  [Enter] open question
```

Approving a gate with failing deterministic checks MUST be impossible; the only path is `waive`,
which requires a typed reason and writes a `WAIVER-###` artifact with an expiry and shows up in
reports. Waivers of `alwaysHuman` gates are not permitted at any autonomy level.

### S6 — Sessions

Facilitated discussions (see `16`). List of past sessions + "start new". During a live session the
screen becomes a transcript pane + a technique/step indicator + an input box, with participating
agent personas shown as speakers.

```

│ pm        What if we removed the setup wizard entirely for trials?       │
│ architect That implies defaults per vertical — a config catalog.         │
│ you       > we can't; compliance needs explicit tax config              │
└──────────────────────────────────────────────────────────────────────────┘
[space] next technique step  [c] converge  [s] save to KB  [Esc] end
```

The fifteen customization surfaces from `15` §15.1 in the left pane, each with a modified-count
badge; the right pane shows the resolved object with **per-field layer provenance** colouring
(built-in / module / org / project / local), plus a live validation strip.

```

│ Agents            (2)  ││ model.tier        balanced          ← project override         │
│ Skills            (4)  ││ persona.voice     "terse, cites…"   ← project override         │
│ MCP servers       (3)  ││ tools.exec        [git*, pnpm*, ./gradlew*]  ← +1 project      │
│ Tool grants       (1)  ││ skills            acme-java-standards ← project                │
│ Workflows         (1)  ││                   tdd-loop-discipline ← built-in               │
│ Gates & checks    (2)  ││ gates.may_approve []                 ← locked (invariant I1)   │
│ Frameworks        (1)  ││ ceiling.network   none               ← module ceiling          │
│ Templates         (5)  │└───────────────────────────────────────────────────────────────┘
│ Voice & style     (1)  │
└────────────────────────┘

```

`t` (test) runs the surface's validation: skill checks, a live MCP handshake with grant-fidelity
verification, or a framework dry-run. Locked fields render with a lock glyph and the invariant id,
so the guardrails teach themselves rather than surprising the user at compile time.

### S7 — Cost & telemetry

Per-run, per-stage, per-agent, per-model spend; token counts; wall-clock; cache-hit indicators if the
adapter reports them; budget burn-down; top-10 most expensive steps; a "cost per merged story" metric.

## 4.4 Modal flows

| Modal | Trigger | Contents |
|---|---|---|
| **Elicitation** | Workflow needs a human answer | Question, why it matters, options with trade-offs, "I don't know — recommend one" escape hatch, free text |
| **Gate review** | Gate reaches `waiting` | As S5, focused |
| **Conflict resolution** | Merge queue conflict | Conflicting hunks, the two lanes' intents, options: `let agent resolve` / `take A` / `take B` / `open editor` |
| **Destructive confirm** | rm/force-push/db-drop/deploy-prod | Command text, blast radius, typed confirmation |
| **Budget breach** | Spend ≥ cap | Spend breakdown, options: raise cap / finish current lanes only / abort |
| **Assumption** | Agent proposes an assumption instead of asking | Assumption text, confidence, impact, `accept` / `ask me instead` / `edit` |

**Elicitation must never be a wall of questions.** Max 3 questions per modal, ordered by information
gain, with the agent's recommended default preselected. "I don't know" is always available and routes
to the relevant decision framework instead of blocking.

## 4.6 State management

- `EngineClient` (in `@forge/tui/state`) subscribes to the engine event stream and maintains a
  normalised read model in a `zustand`-style store (hand-rolled ~80 LOC reducer store is acceptable;
  do not pull in Redux).
- Reducers are pure and unit-tested against recorded event fixtures (`fixtures/events/*.ndjson`).
- The TUI MUST tolerate: out-of-order events (order by `seq`), missing events (gap detection →
  request snapshot), and engine restart (re-subscribe + snapshot).
- Rendering is derived exclusively from the read model. No direct FS reads in components (except the
  artifact viewer, which goes through a cached `ArtifactReader` service).

## 4.7 Accessibility & environment

- Respect `NO_COLOR`, `FORCE_COLOR`, `TERM=dumb` (→ stream mode), `COLUMNS`/`LINES`.
- `--ascii` mode replaces all box drawing and glyphs with ASCII equivalents.
- Screen-reader-ish mode `--linear`: no panes, purely sequential output, every state change announced
  as a line. This doubles as the CI-friendly mode.
- All colours chosen to be distinguishable under common colour-blindness types; never encode
  pass/fail by red/green alone.

## 4.8 Testing the TUI

- Snapshot tests with `ink-testing-library` at 80×24, 100×30, 120×40 for every screen in every
  canonical state (empty, loading, running, blocked, failed, complete).
- Keyboard-driven interaction tests: a scripted key sequence produces an expected command list on the
  engine mock.
- Event-replay tests: feed a recorded run's NDJSON and assert the final rendered frame matches a
  golden file.
- A fuzz test that sends random resize + key events for 10 000 iterations and asserts no crash and no
  unhandled promise rejection.
